# Sanitiser

[![Downloads](https://img.shields.io/nuget/dt/Umbraco.Community.Sanitiser?color=cc9900)](https://www.nuget.org/packages/Umbraco.Community.Sanitiser/)
[![NuGet](https://img.shields.io/nuget/vpre/Umbraco.Community.Sanitiser?color=0273B3)](https://www.nuget.org/packages/Umbraco.Community.Sanitiser)
[![GitHub license](https://img.shields.io/github/license/richarth/sanitiser?color=8AB803)](https://github.com/richarth/sanitiser/blob/main/LICENSE)

When enabled, this package will automatically remove personal data from your Umbraco website on startup.

Out of the box the package will delete member data.

Umbraco versions supported: v13 (on .NET 8), v15/v16 (on .NET 9), and v17/v18 (on .NET 10). A single package version supports them all.

## Packages

Sanitiser is a small family of packages:

| Package | Contents |
|---|---|
| `Umbraco.Community.Sanitiser` | The main package — the built-in user and member sanitisers. This is what most sites install. |
| `Umbraco.Community.Sanitiser.Core` | The `ISanitiser` extension point, orchestration, and the `DatabaseTableSanitiser`/`DirectorySanitiser` base classes. Depend on this directly only when building your own sanitisers or replacer without the built-in ones. |
| `Umbraco.Community.Sanitiser.Faker` | Optional. Replaces personal data with realistic fake values via [Bogus](https://github.com/bchavez/Bogus) |
| `Umbraco.Community.Sanitiser.AI` | Optional. Replaces personal data with values generated by [Umbraco AI](https://docs.umbraco.com/ai-in-umbraco). Umbraco 17.4+/18 only |

The `Faker` and `AI` packages are separate because each brings an extra dependency and changes replacement
behaviour; install one only if you want it. Both depend on `Core`, not on the main package.

## Installation

Add the package to your Umbraco website from nuget:

`dotnet add package Umbraco.Community.Sanitiser`

## Configuration

To enable the package, add the following to your `appsettings.json`:

```json
{
  "Sanitiser": {
    "Enable": true
  }
}
```

### Dry run

Before letting the sanitiser modify anything, you can preview what it would do. With `DryRun` enabled, the
built-in user and member sanitisers log the records they *would* delete or anonymise and make no changes at
all:

```json
{
    "Sanitiser": {
        "Enable": true,
        "DryRun": true,
        "MembersSanitiser": { "Enable": true }
    }
}
```

Because a dry run makes no changes, it is also allowed to run in `Production` so you can safely preview there.
Once you are happy with the logged output, set `DryRun` back to `false` to perform the sanitisation.

> [!NOTE]
> Dry run is passed to every sanitiser via the `SanitisationContext`. The built-in user and member sanitisers
> and the `DatabaseTableSanitiser`/`DirectorySanitiser` base classes all honour it; a custom `ISanitiser`
> should check `context.DryRun` and make no changes when it is set.

### Member Data

To enable the deletion of member data, add the following to your `appsettings.json`:

```json
{
    "Sanitiser": {
        "Enable": true,
        "MembersSanitiser": {
            "Enable": true
        }
    }
}
```

To exclude members whose email addresses belong to specific domains from sanitization, add the following to
your `appsettings.json`. This is intended for your own real domains — accounts on these domains are left
untouched:

```json
{
    "Sanitiser": {
        "Enable": true,
        "MembersSanitiser": {
            "Enable": true,
            "DomainsToExclude": "yourcompany.com,yourpartner.com"
        }
    }
}
```

> [!NOTE]
> The `Faker` and `AI` replacers generate fake emails on the reserved `example.com` domain, so avoid
> adding `example.com` to `DomainsToExclude` — it is meant for your real domains, not the generated ones.

### Delete vs Anonymise

The Members and Users sanitisers support two modes, set via `Mode`:

- `Delete` (the default) — replaces each record's personal data (so values lingering in audit and log
  tables are scrubbed) and then deletes the record.
- `Anonymise` — replaces each record's personal data but keeps the record.

```json
{
    "Sanitiser": {
        "Enable": true,
        "MembersSanitiser": {
            "Enable": true,
            "Mode": "Anonymise"
        }
    }
}
```

### Replacement values

Replacement values are generated by a replacer. The built-in replacer uses templates, where `{index}` is
substituted with a unique number per record:

```json
{
    "Sanitiser": {
        "Enable": true,
        "Replacement": {
            "EmailTemplate": "user{index}@example.com",
            "NameTemplate": "user{index}",
            "UserNameTemplate": "user{index}"
        }
    }
}
```

The values shown above are the defaults. See [Custom personal data replacer](#custom-personal-data-replacer)
for replacing the template replacer entirely.

### Custom database tables

To enable the deletion of data from custom database tables, you can extend the `DatabaseTableSanitiser` class and create
a poco with a table name attribute.

For example, to have a table called `test` automatically emptied on startup, create a poco like this:

```csharp
using NPoco;

[TableName("test")]
public class Test;
```

And extend the `DatabaseTableSanitiser` class like this with your poco class as a type parameter:

```csharp
using Umbraco.Community.Sanitiser.Persistence;

namespace Umbraco.Community.Sanitiser.sanitisers;

public class TestTableSanitiser(SanitiserDbContext dbContext) : DatabaseTableSanitiser<Test>(dbContext)
{
    public override bool IsEnabled()
    {
        return true;
    }
}
```

### Directory sanitization

To enable the deletion of files and folders in a directory, you can extend the `DirectorySanitiser` class and implement the `IsEnabled` and `GetDirectoryPath` methods. `GetDirectoryPath` should return the path you want clearing out. E.g.

```csharp
using Umbraco.Community.Sanitiser.sanitisers;

public class MyCustomDirectorySanitiser : DirectorySanitiser
{
    protected override string GetDirectoryPath()
    {
        return "wwwroot/media/forms/upload/";
    }

    public override bool IsEnabled()
    {
        return true;
    }
}
```

> [!WARNING]
> N.B. This package is not intended to be run on production sites, only enable sanitization on a development or staging
> environment. Before enabling please ensure you have a backup of your data and a backup of your backup.
>
>If there is a lot of data then the startup of your site may be delayed. Only enable when necessary.

### Environments

Sanitisation is skipped only when the ASP.NET Core environment is exactly `Production`. Every other
environment — `Development`, `Staging`, or any custom name — is treated as non-production and **will** run
sanitisation when `Enable` is `true`. In particular, a `Staging` environment is not protected, so treat any
non-production environment as one where data may be removed.

To run in `Production` you must opt in explicitly with `ProductionOverride`, or use `DryRun` to preview
without making changes:

```json
{
    "Sanitiser": {
        "Enable": true,
        "ProductionOverride": true
    }
}
```

## Customisation

### Custom sanitizer

To add your own sanitization logic, implement the `ISanitiser` interface. Your sanitization logic will be run
automatically on startup when the sanitization service and your sanitizer are enabled.

Add your logic to the `Sanitise(SanitisationContext context)` method, and honour `context.DryRun` — when it is
`true`, log what you would change but make no changes:

```csharp
using Umbraco.Community.Sanitiser.sanitisers;

public class MySanitiser : ISanitiser
{
    public bool IsEnabled() => true;

    public Task Sanitise(SanitisationContext context)
    {
        if (context.DryRun)
        {
            context.Logger.LogInformation("[DRY RUN] Would remove X");
            return Task.CompletedTask;
        }

        // ... perform the removal ...
        return Task.CompletedTask;
    }
}
```

You will also need to implement the enabled check in the `IsEnabled` method. You could check for a value in Umbraco,
simply return true or more likely add a setting to `appsettings.json`.

### Custom sanitizer settings

If adding your own setting(s) to the `Sanitiser` section of `appsettings.json`, create an options class for your
sanitiser and bind it to its own sub-section in a composer — the same pattern the built-in Users and Members
strategies use. For example:

```csharp
public class MySanitiserOptions
{
    public bool Enable { get; init; }
}
```

```csharp
using Umbraco.Community.Sanitiser.Configuration;

public class MySanitiserComposer : IComposer
{
    public void Compose(IUmbracoBuilder builder)
    {
        builder.Services.Configure<MySanitiserOptions>(
            builder.Config.GetSection($"{SanitiserOptions.SanitiserOptionsKey}:MySanitiser"));
    }
}
```

If you were to add the following to your `appsettings.json`:

```json
{
    "Sanitiser": {
        "MySanitiser": {
            "Enable": true
        }
    }
}
```

The values will be automatically mapped to your options class, which you can inject into your sanitiser
as `IOptions<MySanitiserOptions>`.

### Realistic and AI-generated replacements

Two optional packages replace the default templated values with more lifelike data. Install either one and it
takes over replacement for all sanitisers automatically — no configuration required beyond the package itself.

> [!IMPORTANT]
> Install only **one** replacer package. If both `Faker` and `AI` are installed they both try to take over,
> and which one wins is not guaranteed.

- **`Umbraco.Community.Sanitiser.Faker`** generates realistic names, emails and usernames with
  [Bogus](https://github.com/bchavez/Bogus). Emails use the reserved `example.com` domain and are made unique
  per record. `dotnet add package Umbraco.Community.Sanitiser.Faker`

- **`Umbraco.Community.Sanitiser.AI`** generates values with [Umbraco AI](https://docs.umbraco.com/ai-in-umbraco)
  (Umbraco 17.4+/18, .NET 10 only). It requires Umbraco.AI to be installed and configured with a chat connection
  and profile. By default it uses your default chat profile; to use a specific one, set its alias. To reduce the
  number of model calls it requests people in batches (default 20 per call); set `BatchSize` to tune this:

  ```json
  {
      "Sanitiser": {
          "AiReplacement": {
              "ProfileAlias": "sanitiser",
              "BatchSize": 20
          }
      }
  }
  ```

  Each record's email and username are made unique regardless of what the model returns. If a call fails or
  can't be parsed, affected records fall back to templated values so a run is never blocked. AI replacement
  still calls a model (once per batch), so it is slower and may incur cost.

### Custom personal data replacer

To change how replacement values are generated for all sanitisers, implement `IPersonalDataReplacer` and
register it in a composer — this is exactly how the Faker and AI packages work:

```csharp
using Umbraco.Community.Sanitiser;
using Umbraco.Community.Sanitiser.Replacement;

public class MyReplacer : IPersonalDataReplacer
{
    public Task<PersonalData> Replace(PersonalData original, int index)
    {
        return Task.FromResult(new PersonalData(
            $"Person {index}",
            $"person{index}@example.org",
            $"person{index}"));
    }
}

public class MyReplacerComposer : IComposer
{
    public void Compose(IUmbracoBuilder builder)
    {
        builder.SetPersonalDataReplacer<MyReplacer>();
    }
}
```

The original values are passed in so your implementation can derive realistic replacements from them.
